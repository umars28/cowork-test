# Slices — notes app: JSON API + server-rendered UI

Test command for every slice (from `.aiflow/project.yaml`): `go test ./...`

| # | Slice | Primary files | Test that proves it |
|---|---|---|---|
| 1 | Domain type and validation. `Note` with its JSON tags, the `ErrNotFound` / `ErrEmptyTitle` sentinels, and the one function that decides whether a title/body pair is valid (trimming, empty-title rejection). Slice 1 comes first because every other slice imports `note.Note` and the sentinels, and because fixing the shape of the type later means touching the store, both handler files and the templates at once. Slice 2 follows so that slices 3 and 4 have something real to serve — a stubbed store would make their tests assert against a fiction. The API lands before the pages because its contract is tighter (status codes, envelope, headers) and the pages reuse the same store calls, so any gap in the store surfaces against the cheaper-to-test layer first. Wiring is last because `main` cannot wire a handler that does not exist yet, and until then the placeholder binary still builds.

Slice 2 carries the most risk. It is the only slice holding the design's named failure mode: tmp-file-plus-rename, fsync of the parent directory, and updating memory only after `Rename` returns nil are three things that all look correct when written wrong, and the test that would catch a mistake is the hardest to write honestly — a concurrent-writer test proves serialization but cannot prove crash safety, which is only reachable by inspection of the write ordering. Slice 4 is the runner-up for a duller reason: `//go:embed` plus `html/template` fails at init rather than compile, so a typo in a template name turns every test in the package red at once.
